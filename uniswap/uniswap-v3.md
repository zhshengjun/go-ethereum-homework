## Uniswap V3

### 1. 集中流动性的优势是什么？

V2 的 LP 资金理论上覆盖 `0` 到无穷大的价格范围，许多远离市场价的资金平时用不上。

V3 让 LP 选一段自己愿意做市的价格区间，把相同资金集中在更可能成交的位置；在区间内，同等资本能提供更深的流动性，使交易的价格影响更小，也可能取得更多手续费。

代价是价格走出区间后该仓位**不再参与交易和赚取手续费，并逐渐变为单一资产**；区间越窄越需要管理，且仍面临价格变化造成的相对损失。

### 2. 集中流动性在合约层面大致如何实现？

LP 用下边界 `tickLower`、上边界 `tickUpper` 和流动性 `L` 定义一个仓位。当前价格处于 `[tickLower, tickUpper)` 时，这个仓位的 `L` 才计入 Pool 的有效 `liquidity`。

Pool 在 `positions` 记录“所有者（`NonfungiblePositionManager`） + 区间”的份额与手续费状态；在上下边界的 `ticks` 记录流动性变化量 `liquidityNet`，并用 `tickBitmap` 快速寻找已初始化边界。

一次 swap 在当前区间内按局部流动性计算价格变化； 当 tick 移动到**已初始化**边界时，`ticks.cross` 更新边界两侧的累计账本， 再按 `liquidityNet` 增减有效的 `L`，继续下一段。

这样不需要每次交易遍历所有 LP 仓位。价格可在两个可用 tick 之间移动，不是每笔交易都跳一整格。

V3 Core 账本记录的是仓位，不是 NFT；只是 Periphery 的 `NonfungiblePositionManager` 才把用户仓位包装成 NFT。

### 3. tick 和价格是什么关系？

tick 是相当于是价格尺度上的整数编号。对原始代币最小单位，V3 用 `P_raw = token1 / token0 = 1.0001^tick` 定义该编号对应的价格；

每向上一个 tick，比例乘 `1.0001`，约增加 `0.01%`，向下则除以 `1.0001`。

Pool 实际存储 `sqrtPriceX96 ≈ √P_raw × 2^96`，`TickMath` 可做 tick 与平方根价格的换算。

读“人类价格”时还要处理 token0/token1 的方向与 decimals：若 token0 有 `d0` 位、token1 有 `d1` 位，则每 1 个 token0 对应的 token1 数量是 `P_raw × 10^(d0-d1)`；要反向报价就再取倒数。

当前 `slot0.tick` 是跟踪价格所在区间的状态，不要求等于某个已初始化仓位边界；边界点与 `sqrtPriceX96` 直接反算的 tick 在跨越瞬间也可能按合约约定相差 1，这个就是看价格移动时的方向，由右向左移（`添加token0`）也就是`state.tick = zeroForOne ? step.tickNext - 1 : step.tickNext;`。

### 4. 为什么 V3 需要 tick？


LP 想选任意价格范围，但链上不能为无穷多个连续价格分别建账。

tick 提供统一的区间边界：仓位只在上下边界登记，Pool 在跨越这些边界时才改变有效流动性；位图帮助快速跳过没有仓位边界的价格区域。

这样的设计同时让仓位范围、手续费结算和交易跨区间计算有可执行的整数索引。

tick 的离散性约束的是**可选仓位边界**，不意味着成交价格只能落在离散点。


### 5. tick spacing 和手续费费率是什么关系？

`tickSpacing = s` 表示一个池只允许 `tick % s == 0` 的 tick 用作仓位上下边界、被初始化。例如 `s=10`，可用边界是 `...,-10,0,10,...`；相邻可用边界的原始价格比是 `1.0001^10 ≈ 1.00100045`，即约 `0.100045%` 的差，不是价格每次只能跳 `0.100045%`。

V3 Factory 用 `feeAmountTickSpacing[fee]` 存一张**配置映射**，建池时据此给 Pool 固定 `fee` 与 `tickSpacing`。本工作区的原始 Factory 构造器预置 `500 → 10`（0.05%）、`3000 → 60`（0.30%）、`10000 → 200`（1%）；`fee` 的单位是百万分之一。

后续也可由有权限的治理方通过 `enableFeeAmount` 增加新费率及其 spacing，已有映射不能在该接口中改写。官方后续文档还列出 `100 → 1`（0.01%）等新增档位，因此不能把构造器的三档误认为所有时期、所有部署的完整清单；实际集成应读目标 Factory / Pool 的链上配置。

### 6. 为什么不同费率池会对应不同的 tick spacing？

这是池设计和 gas 的取舍，并不是“费率代入某个数学公式就自动算出 spacing”。

低手续费池通常面向价格较稳定、频繁交易的资产，较密的可用边界让 LP 更精细地摆放流动性；高费率池常面向波动较大或交易较少的资产，较宽的 spacing 限制可初始化的边界数量。

跨越一个真正已初始化的 tick 要更新流动性及累计账本，会增加 gas；未初始化的可用 tick 不会因为价格经过就执行同样的跨越更新。

较宽 spacing 也提高单 tick 可容纳的最大流动性。具体配对是 Factory 的治理配置，其他新增档位未必严格遵循“费率越高，spacing 必定越大”的数学定律。

说人话就是，**需要控制跨越已经初始化 `tick` 时的 `gas` 消耗，因为价格波动大，`tick` 移动幅度大，容易造成已初始化 `tick` 的跨越，就会计算**。
